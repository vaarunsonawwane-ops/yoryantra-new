A file upload works in one client but fails in another. The form fields look right, and the browser says it is sending `multipart/form-data`. Yet the backend reports a parsing error—or responds with `400` or `415`.

Before changing field names or trying another header, look at the boundary. A multipart request has to tell the server where each part begins and ends. That only works when the boundary named in the `Content-Type` header matches the separators in the request body.

With browser `FormData`, you usually never need to build or copy a boundary yourself. The browser does that when it serializes the request. Problems often begin when application code, an HTTP wrapper, an interceptor, or a manually assembled body interferes with it.

This guide shows what to inspect, why the common fixes sometimes make things worse, and how to separate a broken multipart body from an endpoint that does not accept multipart at all.

## First, understand what the boundary does

A multipart body contains separate parts. Each part has its own headers and content: perhaps a text field, another text field, and a file. The outer `Content-Type` tells the receiver which boundary value separates those parts.

For example, a request might declare:

```http
Content-Type: multipart/form-data; boundary=demo-boundary
```

Its body uses `--` followed by that exact boundary value as a delimiter:

```text
--demo-boundary
Content-Disposition: form-data; name="name"

Sneha
--demo-boundary
Content-Disposition: form-data; name="role"

developer
--demo-boundary--
```

Notice the two extra hyphens at the start of each delimiter and the closing two hyphens at the end of the final delimiter. The header value is `demo-boundary`; the body delimiter is `--demo-boundary`.

The receiver uses the header to identify the delimiters. If the header says `alpha` but the body uses `beta`, the multipart parser cannot reliably separate the parts. RFC 7578 defines this `boundary` parameter for `multipart/form-data`.

Two details matter when reading raw traffic. A header may legally quote the parameter, as in `boundary="demo-boundary"`; those quotes are syntax, not part of the delimiter. Also, the chosen boundary must not accidentally occur in a part in a way that looks like a delimiter. These are reasons to let a capable HTTP client choose it rather than copying a sample value into production code.

## Let Fetch handle the boundary when you use native FormData

This is the normal browser pattern:

```js
const form = new FormData();
form.append("name", "Sneha");
form.append("role", "developer");

await fetch("/api/profile", {
  method: "POST",
  body: form,
});
```

Fetch serializes the entry list and supplies a header resembling `multipart/form-data; boundary=----generated-value`. The same generated value appears in the body. The exact text changes between requests; it is not something your application should depend on.

Now compare the common mistake:

```js
await fetch("/api/profile", {
  method: "POST",
  headers: {
    "Content-Type": "multipart/form-data",
  },
  body: form,
});
```

The application has supplied the header, so Fetch does not replace it with one containing the generated boundary. The body can still contain valid-looking multipart delimiters, but the server has not been told which delimiter to use. MDN explicitly warns against setting this header yourself for browser-generated FormData.

The fix here is not to invent a boundary value. **Remove the manually forced `Content-Type` and let Fetch own both the body serialization and the header.**

## Four controlled requests show the difference

The frozen Yoryantra research reproduced these cases using Node 22.16.0's built-in Fetch and FormData against a strict local HTTP endpoint. The test endpoint inspected the header and multipart framing; it was not intended to emulate every production framework.

| Test request | What the receiver sees | Result in the strict test |
| --- | --- | --- |
| Native `FormData`; no forced header | Boundary matches body | Accepted |
| Native `FormData`; forced header | Header lacks boundary | Rejected |
| Hand-built: header `alpha`, body `beta` | Boundaries differ | Rejected |
| Hand-built: no closing delimiter | Incomplete message | Rejected |

The result to carry forward is the *structural distinction*, not a promised status code. A backend might reply `400`, `415`, another parser error, or a validation response depending on its middleware and route.

### Missing boundary parameter

Suppose the actual request header is only:

```http
Content-Type: multipart/form-data
```

But the body starts with a client-generated delimiter. The request has an identifiable media type, yet no declared boundary. In a browser app, inspect where that header is being set. It may come from a shared `headers` object or an interceptor, not the `fetch()` call you are staring at.

### Mismatched boundaries

This request declares one delimiter:

```http
Content-Type: multipart/form-data; boundary=alpha
```

while the raw body uses another:

```text
--beta
Content-Disposition: form-data; name="name"

Sneha
--beta--
```

The receiver looks for `--alpha`, not `--beta`. This often happens when someone reuses a header from an example while constructing the body separately. A boundary belongs to the specific serialized request; it is not a reusable constant.

### Missing closing delimiter

Even a matching header and opening delimiter may not be enough. A complete body ends with the closing form `--boundary--`. If a hand-built stream stops early or a proxy truncates it, the parser can regard the multipart message as incomplete. This is a framing problem, not a field-validation problem.

## A useful order for debugging a failed upload

Rather than changing headers repeatedly, work through the request in this order.

### 1. Check whether the route accepts multipart

Read the endpoint documentation or inspect its server-side body parser. A JSON-only route may legitimately reject a perfectly framed multipart body. The fact that the same logical fields worked as JSON does not mean the endpoint supports `multipart/form-data`.

If the route accepts only `application/json`, keep JSON—or deliberately change the server contract. Boundary changes cannot make an unsupported media type acceptable.

### 2. Look at the actual outgoing Content-Type

Open Chrome DevTools, select **Network**, reproduce the request, and inspect **Request Headers**. For native browser FormData, you generally expect a value like:

```http
Content-Type: multipart/form-data; boundary=...
```

If the boundary is absent, look for code that manually sets the header. If the header still says `application/json`, an old JSON default may have survived after the client switched its body to `FormData`.

Be aware that DevTools often presents multipart **Payload** as a parsed form-field view rather than raw bytes. That view helps you check the fields, but it may not expose every delimiter byte. For wire-level evidence, use a controlled echo endpoint, a debugging proxy, or carefully scoped backend request logging. Don't log credentials or uploaded private files while troubleshooting.

### 3. Find who actually serializes the body

Follow the request's **Initiator** and check for a shared API helper, Axios instance, interceptor, generated SDK, or middleware that changes headers after you construct FormData. The line creating `new FormData()` may be correct while a different layer breaks the request.

Browser-native Fetch and Axios do not always travel through the same serialization path. Axios can accept a native FormData instance, and it also offers automatic object-to-FormData serialization. Its documented behaviour depends on the environment and serializer configuration. Use the guidance for the actual client and runtime rather than applying a generic browser rule to every Node library or hand-built request.

### 4. Compare a successful request, not just the field values

If the upload works in Postman, cURL, or an older client, compare the actual `Content-Type`, boundary parameter, method, part names, file-part headers, and any transformations by intermediaries.

Two requests can contain the same `name` and `avatar` values while differing completely in HTTP representation. That is often the explanation for “same data, different result.”

### 5. Check the body and intermediaries if the header looks right

When you are constructing multipart bytes manually, inspect the exact delimiters, CRLF formatting, part headers, and closing delimiter. Check whether a stream ended early or a proxy, gateway, or serverless adapter transformed the body. A displayed boundary parameter is only half of the evidence; the raw body has to agree with it.

If the client is native browser FormData, manual byte assembly should rarely be necessary. Prefer reducing the request to a small working example before adding wrappers back one at a time.

## Don't confuse a boundary problem with a JSON or field-name problem

Here is a different failure:

```js
const form = new FormData();
form.append("name", "Sneha");

await fetch("/api/profile", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: form,
});
```

Now the header claims the body is JSON even though Fetch is sending multipart content. Before checking the boundary, correct the media-type mismatch and confirm that the endpoint accepts multipart.

A separate issue appears with nested field names such as `user[name]`, `user.name`, or `tags[]`. All three can be carried in a valid multipart body. Whether the backend reconstructs a nested object or array from those names is a **parser-contract** question. The boundary only separates parts; it does not interpret their meaning.

This distinction also separates JF-2 from our other articles. JF-B explains why a route may reject a changed media type. JF-1 explains the different ways nested JSON can be represented as form fields. **JF-2 is about the wire framing that allows a multipart parser to read those fields in the first place.**

## Why 400 and 415 don't tell the whole story

It is tempting to diagnose from the status code alone, but parser errors travel through frameworks differently.

A malformed boundary may produce `400 Bad Request`, a framework-specific multipart parsing message, or an error later when the application receives an empty or incomplete parsed body. A route that doesn't support the submitted representation may return `415 Unsupported Media Type`. RFC 9110 defines 415 in terms of unsupported request content format or content coding.

These categories help narrow the search, but they do not identify the exact broken layer. Use the status code alongside the actual header, body and server error. If the network request is blocked by a CORS preflight before your application receives a response, investigate that separately; it is not proof of a broken multipart boundary.

## A short checklist before you change more code

1. Confirm that the API endpoint accepts `multipart/form-data`.
2. Identify whether Fetch, Axios, another library, or your code creates the multipart body.
3. For native browser FormData, remove a manually forced `Content-Type` header.
4. Check that the declared boundary matches the body delimiters and that the closing delimiter is present.
5. Look for a shared JSON header, interceptor, gateway, truncated stream, or request wrapper.
6. Once framing succeeds, troubleshoot field names, repeated arrays, files and server-side validation.

That order saves time because it separates **can the server parse this multipart message?** from **does the server understand the fields inside it?**

## The practical rule

For a complete multipart request, **the header's boundary value and the body's delimiters must describe the same serialized message**. If you are using native browser FormData, the simplest reliable approach is to let the browser set the multipart header and boundary together.

If a request still fails after that, stop guessing: check the endpoint's accepted format, inspect what actually went over the wire, and work outward through the client wrapper and backend parser. That turns an obscure upload error into a small set of testable questions.
