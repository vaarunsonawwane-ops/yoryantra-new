Your sitemap passes validation, and Search Console says `Success`. Yet some of its URLs are missing from Google Search. The results are not contradictory: **sitemap validity, Google's ability to read the file, discovery of individual URLs, crawling and indexing are different things**. Google may use the submitted URLs for discovery, but submission does not put every page into a guaranteed crawl queue. A URL can remain unvisited, fail when fetched, or be assessed without being selected for the index.

Before changing the XML, find out which part of that process is failing for an important URL. The Sitemaps report answers questions about the file; Page indexing and URL Inspection provide evidence about individual pages. Knowing which report to use prevents a lot of unnecessary regeneration and resubmission.

## What did the sitemap validation actually prove?

The word *valid* gets used for three different checks:

1. **Well-formed XML.** An XML parser can read the document. It could still have the wrong root or namespace for a sitemap.
2. **Valid Sitemap protocol content.** The file has the expected `urlset` or `sitemapindex` structure, namespace, `loc` entries, URL format and protocol limits. The Yoryantra Sitemap Validator checks this layer, including duplicates, `lastmod`, and default deployment scope when you supply the sitemap location.
3. **Successful processing by Google.** A `Success` status in Search Console means Google fetched and read the sitemap without errors. It is a report about the sitemap file, not a promise about every page listed inside it.

These checks are related, but they don't collapse into one result. A locally valid file can be inaccessible after deployment. A successfully processed file can contain URLs that redirect, carry `noindex`, or aren't crawled. And an accessible, indexable page can still be left out of Google's index. The validator does not fetch the listed pages; Search Console is needed for Google's observed status.

## A listed URL is not the same as a fetched page

Suppose your sitemap contains:

```xml
<url>
  <loc>https://example.com/guides/api-auth</loc>
</url>
```

The sitemap identifies a URL you prefer Google to discover. It does not deliver the page content. If Google attempts a crawl, it has to request:

```text
https://example.com/guides/api-auth
```

That request can encounter a robots.txt restriction, an authentication response (`401`), forbidden access (`403`), a missing page (`404`), server errors (`5xx`), an unintended redirect chain or a DNS/network failure. Even a successful `200` response isn't proof that Google will select the content for indexing.

The sitemap cannot override these conditions. If the file itself is healthy, use URL Inspection to distinguish a page Google hasn't crawled from one it fetched and evaluated.

## Rule out a sitemap fetch or structure problem first

In Search Console's **Sitemaps** report, check:

- Search Console sitemap status;
- `Last read`;
- whether the file can be fetched;
- whether the submitted location serves the expected file;
- XML/Sitemap protocol errors, absolute URLs, default scope and sitemap-index relationships;
- the 50 MB uncompressed and 50,000 URL limits for an individual sitemap file.

If Search Console reports `Couldn't fetch`, investigate availability, redirects, authentication and the submitted address. If the file has parsing errors, correct those. A validator result from your computer cannot prove that Google received the same bytes from the live sitemap URL.

If the report says `Success`, move to the individual URLs. Also check the `Last read` date: a successful read before your latest deployment does not prove Google has processed the new file. Google may recrawl a sitemap on its own schedule; repeated submission of an unchanged successful file is not a solution to a page-level exclusion.

## Check which URLs the sitemap lists

A sitemap is not supposed to be a dump of every URL your application can generate. Google's sitemap guidance says to include the URLs you want to see in Google Search results. That usually means the preferred, canonical versions. Good sitemap candidates look like:

```text
https://example.com/products/red-shirt
https://example.com/guides/api-auth
https://example.com/about
```

Potentially contradictory entries include an HTTP URL that redirects to HTTPS, an old slug that redirects to its replacement, a tracking-parameter duplicate, a page with `noindex`, an alternate URL that points to a different canonical, or a deleted `404`/`410` URL.

Google can process a sitemap containing one of those URLs. That does not make the URL a good indexing candidate.

## Sitemap inclusion is a canonical signal, but a weak one

This becomes important when the listed URL conflicts with other canonical signals. Google's guidance treats redirects and `rel="canonical"` annotations as strong preference signals, while sitemap inclusion is a weaker one. These signals can reinforce each other; no single hint forces the result.

Suppose the sitemap lists:

```text
https://example.com/product/red-shirt?sort=popular
```

but the page declares:

```html
<link
  rel="canonical"
  href="https://example.com/product/red-shirt"
/>
```

and internal links also point to the clean URL. The sitemap does not force the parameter URL to become canonical. Google still evaluates the duplicate relationship and can choose the clean URL. This is why sitemap troubleshooting often becomes canonical troubleshooting.

## Read Page indexing before deciding what to change

After Search Console has processed the sitemap, filter the **Page indexing** report to the submitted sitemap where that filter is available. Choose one important missing URL and open URL Inspection. The indexed information reflects Google's last recorded view; **Test live URL** checks current accessibility and some indexing signals, but cannot tell you whether Google will choose to index the page later. Always compare the last crawl date with your deployment date.

### Discovered but not crawled

`Discovered - currently not indexed` means Google knows the URL but has not crawled it yet. A sitemap may have helped Google discover it, but discovery does not promise a fetch. Check that the URL is internally linked from relevant pages, the site responds reliably, and the submitted sitemap isn't crowded with stale or unwanted addresses. There can also be crawl-scheduling reasons you cannot resolve from the status label alone. Google's documentation doesn't identify one universal fix; repeatedly changing valid XML is unlikely to help.

### Crawled but not indexed

`Crawled - currently not indexed` means Google fetched the page and did not index it. The next investigation belongs on the page, not in the XML. Compare the recorded HTTP response and rendered content with the current page. Look for a soft-404 interpretation, duplicate content, a canonical pointing elsewhere, or a meaningful difference between the user's intended page and what Google saw. Check meta robots and `X-Robots-Tag` too, even though an explicit `noindex` normally receives its own report reason.

Do not label every page in this state “low quality.” Search Console says it may or may not be indexed later, and explicitly says there is no need to resubmit the same URL for crawling solely because of this status. If the page is accessible and useful, record the evidence and monitor after future crawls instead of making unsupported changes.

## When the page conflicts with the sitemap

Other Page indexing reasons identify a concrete mismatch between your preferred URL and the live site's behavior.

**Indexing instructions.** `URL marked 'noindex'` means Google found an instruction not to index the page. It may come from HTML such as `<meta name="robots" content="noindex">` or an `X-Robots-Tag: noindex` response header. If exclusion is deliberate, remove that URL from the sitemap. If it should appear in Search, remove the accidental directive and verify the live response. A sitemap cannot override `noindex`.

**Crawl permission.** `URL blocked by robots.txt` means the relevant rule prevents Google's crawler from fetching the page. A listing in XML does not grant access. If you intended to allow indexing, correct the winning robots rule; if you intended a private or blocked path, it probably should not be in your preferred-URL sitemap. Blocking a page in robots.txt can also prevent Google from seeing a `noindex` or canonical directive on that page, so the controls should not be treated as interchangeable.

**Redirects and removals.** `Page with redirect` commonly points to a stale sitemap entry. If `http://example.com/guide` redirects permanently to `https://example.com/guide`, list the final URL instead. For a page permanently removed without a replacement, a genuine `404` or `410` is appropriate and its obsolete sitemap entry should go. If it moved, redirect to the relevant replacement and list that new URL. Neither case requires recreating every sitemap entry.

**Duplicates and canonicals.** A submitted URL can appear under `Alternate page with proper canonical tag`, `Duplicate without user-selected canonical`, or `Duplicate, Google chose different canonical than user`. Compare the user-declared canonical with Google's selected URL, inspect the redirect path and internal links, and decide whether the pages are truly duplicates. Usually the sitemap should list the preferred canonical, but it cannot force Google to use it. These statuses deserve a canonical investigation, not XML-format troubleshooting.

## Match the indexing reason to the next action

Use this table after reading the reason for one URL. It distinguishes cases where the sitemap itself should change from cases where it is only a discovery signal.

| URL status | Next check | Change the sitemap? |
| --- | --- | --- |
| `Discovered - currently not indexed` | Internal discovery links and crawl history | Usually no |
| `Crawled - currently not indexed` | Live content, fetch result, canonical and indexing evidence | Usually no |
| `URL marked 'noindex'` | Whether exclusion is intentional | Remove intentionally excluded URL; otherwise fix `noindex` |
| `URL blocked by robots.txt` | Intended crawl permission | Only if URL should not be included |
| `Page with redirect` | Final preferred destination | List final URL |
| `Not found (404)` | Deleted page or replacement | Remove or replace stale URL |
| Duplicate or alternate canonical | User-declared and Google-selected canonicals | Align with preferred canonical |
| Indexed | No indexing issue to diagnose here | No |

## A locally valid sitemap can still fail after deployment

There is another important distinction between local validation and live use. You can paste perfect XML into a validator:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://example.com/page</loc>
  </url>
</urlset>
```

and get a clean result. Yet the live sitemap URL could return `404`, require authentication, time out, be blocked from fetching, or serve a different generated version. The address you submitted might even be different from the one you tested locally.

A browser-side XML validator cannot verify those deployment conditions. Yoryantra's Sitemap Validator checks the pasted content and optional location rules without fetching the file. Use Search Console's reported `Last read` and processing outcome for Google's view. If the deployed sitemap changes automatically during builds, compare the current served XML with the generated output; a correct local file is no help when the wrong artifact is deployed.

## `lastmod` can help scheduling, but it is not an indexing switch

Google says it uses `<lastmod>` when the value is consistently and verifiably accurate. The date should represent the last significant update to the page. For example:

```xml
<lastmod>2026-10-08</lastmod>
```

would be appropriate if the main content, important structured data, or meaningful links genuinely changed on that date. Rewriting every entry to today's date whenever the XML is regenerated makes the field less trustworthy. A reliable `lastmod` may help crawl scheduling; it does not promise a same-day crawl, inclusion in the index or a better ranking. Keep the value tied to the page, not the build timestamp.

## Repeated sitemap submission is not an indexing strategy

If Search Console already shows `Success`, submitting the same unchanged sitemap again does not create a new indexing guarantee. Google's crawling troubleshooting guidance explicitly advises against submitting an unchanged sitemap multiple times per day. Request Indexing in URL Inspection also has limits and does not guarantee inclusion. After a meaningful fix, those features can help Google discover the new state; they are not substitutes for finding the underlying problem.

## A worked diagnosis: the sitemap is fine, the URL is missing

Suppose the Sitemaps report shows `Success`, with a `Last read` date after your latest deployment. Its XML contains `https://example.com/guides/api-auth`, and the page is linked from the main guides index. The URL still doesn't appear in Google Search. The following are **illustrative** Search Console findings, not results from a real property.

**First finding: `Crawled - currently not indexed`.** URL Inspection shows a crawl after publication. The live page returns `200`, allows indexing, has a self-referencing canonical, and displays the complete guide. Those checks rule out several straightforward technical blockers, but they do not reveal why Google declined to index it. Now compare the guide with related pages: does it answer a distinct question, contain the material promised by its title, and avoid rendering errors or substantial duplication? Record the last crawl and wait for a later reassessment if there is no specific defect to fix. Regenerating the sitemap would change none of that evidence.

**Second finding: `URL marked 'noindex'`.** Suppose the production response contains `X-Robots-Tag: noindex` because a staging header rule reached production. The file can remain valid and Search Console can still report `Success`. The fix is to correct the response header, verify that the live URL now permits indexing, and request another crawl if appropriate. Change the sitemap only if the page was intentionally excluded.

**Third finding: `Page with redirect`.** The submitted `/guides/api-auth` URL now redirects to `/guides/api-authentication`. In that case, update the sitemap and internal links to the final preferred address, verify the redirect, and check the destination's own indexing status. A redirect report is about the old address; it does not prove the new page was indexed.

The three cases begin with the same healthy sitemap and require different actions. That is the boundary the [Yoryantra Sitemap Validator](https://yoryantra.com/tools/sitemap-validator) cannot cross: it can check XML and protocol rules, not Google's live crawl history or indexing decisions. Keep the sitemap accurate, then troubleshoot the page the evidence points to.
